# Version log

Every change of plan, what went wrong, and what replaced it. Numbers come from the scripts in this repo.

| Version | What changed | What we found | Lesson / decision |
|---|---|---|---|
| v0 (plan) | "Probability an oblast is under alert in the next N hours", gradient boosting on lag features | Official alerts are issued per raion since late 2025. In Kharkiv oblast some raion was under alert 2,045 of 2,208 hours, 93 % (Jun–Aug 2026; first quoted as 2,084 — an overcount from episodes crossing the period boundary, corrected by `src/audit.py`): "oblast under alert" is almost always true and useless to a person in the city | Target = a **new alert (onset)** at a **specific place**, for 1/3/6/12/24 h, chosen from user scenarios (commute, night, business day, crews, logistics) |
| v0.1 (data audit) | Assumed: the two alert datasets agree on start times, only end times are unreliable | Wrong. Kyiv City Jun–Aug: only 51 % of volunteer starts within 5 min of an official start; 115 vs 161 alert hours; 23 % of recent Kyiv volunteer alerts have a guessed end (start + 30 min) | Never assume two sources measure the same thing; cross-check before modelling |
| v0.2 (data audit) | Assumed: official dataset stops on 7 Sep 2026 because its parser broke on a new message format | Wrong. The official channel's own export ends on 7 Sep 2026 09:09 Kyiv time, at message 338380 — the id where the parser stopped. The channel went silent | No official alert data exists after 7 Sep. Decision: build **both** pipelines — volunteer (latest period) and official (main-city level, ends 7 Sep) |
| v0.3 (data audit) | Air Force channel used to arbitrate between sources | Volyn / Lviv volunteer series: 355 / 342 alert starts vs 81 / 95 official; an Air Force message mentions the oblast within 30 min of only 1–3 % of volunteer starts (7–16 % for official) | Volunteer data contains alerts no other source supports in some western oblasts; reported per location, not hidden |
| v1 | Telegram exports parsed (HTML, not JSON) | Export tooltip prints "UTC+02:00" even in summer. Parsing the wall clock as Europe/Kyiv matches the clock written inside 99 % of alert messages to the minute | Timezone checked against the data itself, not assumed |
| v2 | Feature pipeline + streaming-vs-batch leakage test | Test rebuilds everything from rows known at t (running alerts with unknown end) for 24 random times per source; batch = stream exactly. A deliberately planted leak (using a running alert's true end) was caught | The test is shown to fail when it should |
| v3 | First models: logistic regression vs histogram gradient boosting (LightGBM-style; PyPI blocked here, so scikit-learn's), training window and model chosen on validation, always the full feature set. Text features = raw message counts | Volunteer test: barely above the seasonal baseline (Brier skill +0.02 at 1 h, −0.01 at 3 h); calendar-only model far below it (−0.21 at 3 h). Official test: adding text **hurt** at 3 h (+0.141 → +0.038) | Two problems: drift (models average months, baseline uses 28 days) and "more features ≠ better" (as in the tokamak v5) |
| v3.1 (diagnosis) | Looked at the Air Force channel over time | Posting volume tripled (≈2,000 → 6,345 messages/month by Sep 2026); a new 🏍 emoji for jet drones replaced most 🛵 posts in Aug–Sep 2026 | Raw text counts mean different things in train and test |
| v4 | (a) recent-rate features from finished labels only (+ test, + planted-leak check); (b) text counts divided by their own trailing-28-day level, jet-drone flag; (c) feature set chosen on validation, not "always all" | Official: text no longer hurts at 3 h (+0.136 without vs +0.134 with). Volunteer 12–24 h: still far below baseline (−0.42/−0.58 for "+recent rates") although AUC ≥ baseline | Ranking fine, calibration lagging: test weeks more intense (24 h onset rate 0.87 vs 0.785 in validation, models predicted 0.76) |
| v5 | Online recalibration: every hour, shift log-odds by observed − predicted onset rate over the past week of **finished** labels (+ test, + planted-leak check). Validation decides on/off together with model and window | Validation chose it in 9 of 10 (source, horizon) cases — all but volunteer 24 h. Volunteer test skill now +0.035 / +0.041 / +0.029 / +0.058 at 1/3/6/12 h; 24 h selected config −0.053 (validation picked no recalibration there; not overridden with the test-best variant) | Final version. Negative results kept as they are |
| v5.1 | Report fixes | "Median lead" column dropped: with hourly forecasts it only reflects where the onset falls in the hour grid. Chart legend moved off the data; off-scale points labelled | Show only metrics that mean what they say |

## Kyiv commuter forecaster (12 Oct 2026)

Focus moved to Kyiv commuters (scenarios: Arsenalna — wait for the all-clear or reroute via Zvirynetska; Livoberezhna —
cross the Dnipro by metro before an alert closes the surface stations). Forecasts every 15 min, 15–180 min ahead.

| Version | What changed | What we found | Lesson / decision |
|---|---|---|---|
| k0 (audit) | Claimed earlier: "4,141 official Kyiv alerts since 2022, durations 49 → 30 min" | Wrong count: the official dataset stores most Kyiv alerts **twice** (4,141 rows = 2,267 episodes). Medians were unaffected (duplicates have equal durations) | Always count merged episodes, not rows |
| k0.1 | New system found: since 6 Sep 2026 Kyiv has yellow (drone danger) / red (missile, massive attack) levels, "a new alert replaces the previous one" | The official channel went silent the next day; the volunteer series captures only 157 of 242 Kyiv alerts after the switch, and 29 % of those have a guessed end | Neither existing source is usable for Kyiv after 6 Sep |
| k1 | Labels from the KMDA channel (fixed templates: start, yellow, red, level change, all-clear; one-pass state machine that works in real time) | Matches official episodes 99–100 % (starts and all-clears within 5 min, median offset < 0.1 min) for 2022–2025. From 24 Aug 2026 KMDA has ~50 alerts/week vs 32 and 22 in the official channel: the escalation began two weeks before the level switch and the official channel had already stopped carrying many Kyiv alerts | KMDA = the label source for the whole period (it is what metro closures follow); official kept as the cross-check |
| k1.1 | Alert-map channel checked as a replacement regional source | It stopped mirroring official alerts in Sep 2025 | Regional alert history after 7 Sep comes only from the volunteer data (starts only; its end times are unreliable) |
| k2 | Text signals from 4 channels (Air Force, alert map, Monitoring UA, Mykolaiv Vanek): Kyiv target, Kyiv oblast, toward Kyiv, explosions, threat types | Spot checks: "toward Kyiv" also fired for drones leaving the region; Air Force morning summaries counted as live threats; "Відбій загрози балістики" counted as a threat | Added a direction rule ("з/із/с/від" before the Kyiv mention = away), summaries excluded, all-clears as their own signal. Known miss: "via Chornobyl/Dymer towards Zhytomyr oblast" |
| k2.1 | Testing claims from a pasted AI answer (strategic aviation, ships, 150 km/h Shaheds) against Air Force data | Strategic aviation / MiG-31K / ships precede only 2–5 % of Kyiv alerts; "drones in Sumy/Chernihiv" precede 86 % but barely raise the odds; "drones heading to Kyiv" is the useful signal (2–2.5× the base rate); ~60 % of drone posts in Sep 2026 are jet drones, so the 1–3 h lead rule is outdated | Use measured, not assumed, value of channels |
| k3 | 15-min features from event lists, streaming-vs-batch test | First planted leak was NOT caught — the leaky feature read a fixed copy of the full data, so stream and batch got the same wrong value. Rewritten as a realistic bug (reads the inputs it is given): caught | A leakage test is only as good as the leak you plant |
| k4 | First validation run | Logistic regression predicted ~0 % where 28 % of slots had an alert within an hour (log-loss 0.81–0.95 vs baseline 0.60). Cause: a `two_level_system` dummy seen on a few days of training data became a z-score of ~16 after standardisation | Dropped the dummy, clipped standardised inputs to ±5, kept regime adaptation to recent-rate features and recalibration |
| k5 | Online recalibration (past week of finished outcomes, out-of-sample) and "baseline only" as explicit candidates | Validation (4 weekly refits, 24 Aug – 20 Sep): onset — logreg, no recency weighting, recalibration: 0.497 with all features vs baseline 0.602; recency weighting hurt (fewer effective samples); boosted trees lost to the baseline (0.628 / 0.652). All-clear — every all-feature model lost to the duration baseline (0.565, trees 0.616); with feature groups up to the alert-map channel it wins (0.545) | Feature groups chosen per task on validation |
| k5.1 | Feature ablation on validation, both tasks | Best set for both: Kyiv history + regional alerts + Air Force + alert map (onset 0.484, all-clear 0.545). Adding Monitoring UA and Mykolaiv Vanek made both worse. (The onset run predates the "baseline only" candidate; its baseline, 0.602, is far behind every row, so the choice is unaffected) | Measured value of the volunteer channels: none on top of the Air Force and the alert map |
| k6 | Test, run once per task with the frozen choices (21 Sep – 11 Oct 2026, weekly refits) | See README. Ablation on test is reported for information only; nothing was changed after it. The Livoberezhna "≤ 10 % caught" rule tuned on validation broke on test (16 % caught); fixed-threshold risk bands were added afterwards as a re-tabulation of the same predictions | Absolute risk moves week to week: show risk levels, not guarantees |
| k6.1 | Saved models failed to load in `forecast.py` | `train.py` ran as `__main__`, so pickles pointed at `__main__._signed_log` | Transforms moved to `kyiv/model_utils.py`; final models refitted |
| k7 | Full rerun from a fresh clone (data download, leakage tests, tables, validation, test, final, forecast) | Same choices, same test predictions (max difference 1e-5, CSV rounding), same forecast output | Reproducible |
